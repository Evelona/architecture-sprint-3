# Задание 1. Анализ и планирование


### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.

**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс
- Система получает данные о температуре с датчиков, установленных в домах

### 2. Анализ архитектуры монолитного приложения

**Язык программирования:** Java\
**База данных:** PostgreSQL\
**Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.\
**Взаимодействие:** Синхронное, запросы обрабатываются последовательно.\
**Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.\
**Развёртывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

Оринтируясь на ДДД, по текущим вводным я бы выделила за основу 2 микросервиса - Управление устройствами и Мониторинг. Но, опираясь на жиненный опыт добавила бы еще 3 микросервиса, которые бы точно пошли на пользу приложению: сервис Нотификаций, сервис Авторизации и управления учетками и сервис Истории действий

**Микросервис Управление устройствами**
- основной задачей этого сервиса будет давать пользователям возможность
включать/выключать устройства умного дома. В качестве взгляда на будущее
можно отнести сюда же добавление пользовательских сценариев,
регистраций новых устройств, управлением контролем доступа

**Микросервис Мониторинга**
- основной задачей этого сервиса будет сбор данных с датчиков
умного дома и отбражение различных графиков. На будущее сюда
можно отнести - создание алертов, при определенных нарушениях
норм в показателях, хранениен истории вычислений

**Микросервис Нотификаций**
- основной задачей этого сервиса будет информировать пользователя
по предпочитаемому каналу связи - почта, смс, уведомление

**Микросервис Авторизации и управления учетками**
- основной задачей этого сервиса будет управление профилями
пользователей (регистрация, восстановление), тут же назначение ролей
и прав доступа и вероятно можно добавить интеграцию с сервисами авторизации

**Микросервис Истории действий**
- основной задачей этого сервиса будет сохранение истории действий умного дома

### **4. Проблемы монолитного решения**

- Первой проблемой выделю - синхронность всех операций.
Синхронность это конечно хорошо (данные будут достоверны),
но в случае этого приложения такие опирацию будут плохо влиять
на пользовательский опыт. Чтобы узнать включено/выключено отопление
дома нужно подождать пока дойдет запрос до бека, который отправит
свой запрос до датчика дома (и дай бог он будет только один,
а не 5 для каждой комнаты). А когда будут реализованы запросы
бизнеса на расширение количества управления устройсвами приложение
будет думать очень долго
- Второй проблемой является сложность масштабирования.
При запросе бизнеса внедрения новых фич, монолитному приложению сложнее релизиться.
Новые изменения в одной части приложения могут положить
другую часть - из-за этого появляется сложность и важность
внимательного тестрирования
- Развёртывание монолитного приложения требует остановки
всего приложения - это значит в момент обновления
приложения, например, пользователи не смогут использовать функции приложения - что
тоже влияет на пользовательский опыт. Плюс тут необходимо учитвать
то, что это монолит и приложение будет развертываться дольше,
чем могли бы микросервисы
